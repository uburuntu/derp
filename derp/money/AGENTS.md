# Money — wallets and the ledger

- Owns `wallets` (one per user and per chat), `credit_lots`, `reservations` + `reservation_holds`, `ledger_entries` and `run_fees`. Amounts are integer Derpcoins; `Settings.credits_for_usd` converts provider cost.
- A balance is the sum of unexpired lots' `remaining`. Lot sources: `plan` (cycle allowance, expires), `purchase`, `sponsored` (a day's allowance, expires), `grant`, `migration`. Lots are spent soonest-expiring first, then oldest.
- `wallets.py` is the only writer. Every movement locks the wallet row first (serial per wallet, so never negative) and is keyed by a caller-chosen operation ID (`run:<id>`, `stars:<charge id>`…); repeating an operation returns the first result. `wallets.empty_noticed_at` is a notice flag, not money: `Funder.ran_dry` sets it, a purchase, an owner `/grant` or a wallet able to pay again clears it.
- Flow: `reserve` (full amount, or at least `minimum`, from chosen sources) → `capture(actual)` spends from the holds and returns the rest; the charge never exceeds the hold, the difference is eaten, never owed. Returning credits to a lot that expired meanwhile expires them; to a refunded (`revoked_at`) lot claws them back, so a refund during a run never resurrects credits. A held operation id funds only its own wallet and only while held. `release` = capture 0; `stale_holds` lists holds of crashed processes (the app skips ids a live run owns and releases each in its own transaction); `expire_lots` runs every few hours.
- `expire_lots` and `claw_back` (refunds: takes only what is left of a lot; spent credits are not recovered) write their own entries.
- DB guarantees: `CHECK 0 ≤ remaining ≤ amount`, captured ≤ held, ledger entries positive with unique (operation, kind, lot), and a trigger rejecting UPDATE/DELETE on `ledger_entries`.
- Invariant (tested): per lot, `amount − remaining = hold − release + expire + clawback`; `capture` entries record spending and do not change the lot.
- `funding.py`: `Funding` (paid → standard chat model, sponsored → cheap model, free) and `Funder`. Payer order — private: own paid lots → own sponsored daily lot; group: chat's paid lots → invoker's paid lots (unless they turned off `users.group_spending`) → invoker's sponsored lot. A payer is used only if it covers a typical turn on its tier's model (prompt prefix from `Funder(prefix=…)` + half the window in, a short answer out, uncached) (an action of known price passes `paid_minimum`: paid lots only, from the first payer that covers it plus a typical turn to carry on from it); it reserves up to `run_caps.credits`, and that hold is the run's money cap. The sponsored lot is credited lazily per UTC day; sponsorship stops at `sponsored_global_daily_usd` (summed from `provider_calls`, one owner ping per day).
- Free models (`Funding.FREE`, nothing held, nothing charged) are the last rung and only when allowed: in private chats after the person consented (`users.free_models_consent_*`, current `free.POLICY_VERSION`), in groups after an admin enabled `chats.free_models`. `free.py` owns the offer shown when nobody can pay or when someone asks for free models (consent / admin-enable button; only that press turns them on, never a tool or the model), the public notice on enabling, and the waiting question: every unfunded ask becomes the person's waiting question in that chat (`chat_members.waiting_message_id`/`waiting_at`, newest wins). For `waiting_minutes`, and while no newer ask of theirs there got an answer, it is resumed by the presses of `Unblock` buttons (callback prefix `free`): consenting / enabling free models, or Continue, which `offer_continue` posts (replying to the question) after a purchase for the buyer's own waiting question in the chat and topic the purchase was for. Only the asker may press Continue, so a patron's top-up never replays other people's asks. `claim` takes the question atomically (row lock), so double presses answer it once; the answer is an ordinary `Runtime.answer` of the original message (same requester, chat, topic, funding rechecked, `turn:` operation id); a stale one (expired, superseded) turns the Continue line into a plain note. The offer names the refill time as a `tg://time` date-time entity (each reader's own clock) and leads with buying (`billing.menu.buy_button`): in private Buy Derpcoins (edits the offer into the buy menu in place, Use free models kept) then Use free models; in groups Top up this chat (the chat's pack menu, ephemeral for the presser) then the admins' free-models button. In groups each person gets it at most once per chat per UTC day (`chat_members.offered_on`, `offer_due`); later unfunded calls get a 🙈 reaction on the ask and nothing else (`answer_unfunded`).
- Empty chat wallet: after a run charged a chat wallet, `Funder.ran_dry` (its own transaction, after the charge committed) reports once when the wallet can no longer pay a typical paid turn; then one silent line with a top-up button says the askers' own Derpcoins pay from here (`free.note_empty_wallet`, called by the runtime after every settled charge). Not again until a top-up.
- `Funder.settle` charges `credits_for_usd(sum of the run's provider_calls)` plus the run's `run_fees` (flat Derp fees such as heavy media effects; never provider spend, so they stay out of the provider ledger and cost stats) only when Telegram accepted an output (message, tool output or reaction); otherwise the hold is released. A background task releases holds older than the run timeout + 10 min unless a live run in this process still owns them.
- `command.py`: `/credits` (Derp+ left and until, bought, free today, the chat's balance and who chipped in lately (`billing.patrons.lately`); admins also see who spent the chat's Derpcoins in 30 days) and `/info` as a reply to any Derp output (model, tokens, context, tool calls, charge and who paid). Both are ephemeral commands in groups; sent the ordinary way, the answer goes by DM (or a plain hint to open the private chat) and never into the group.
- All wallet functions run inside the caller's transaction; never hold one across Telegram or provider calls.
