# Agent

- `models.py`: `agent_runs` (one row per invocation: trigger, funding, served model, usage, cost, charge, Pydantic AI history) and `run_outputs` (every delivered message/poll/sticker/image/reaction, so `/info` resolves any output to its run).
- `runs.py` owns the run lifecycle. `finish_run` is the single place that ledgers a run's provider responses and stores its history; stored history replaces inline binary with markers and follows the chat's retention.
- Tools never receive `chat_id`/`user_id` arguments; scope comes from run dependencies.
- `invocation.py` decides what invokes Derp: every private message; in groups @mention/text mention, replies to Derp, or Derp's name (en/ru inflections and diminutives, not compounds). Bots never trigger (loop guard), anonymous admins do. Commands are a separate trigger kind handled by routers.
- `context.py` builds the recent window before the current message: members' messages become `<chat_history>` transcript blocks (untrusted data), Derp's replies are replayed from their completed runs (tool calls + clipped results, no thinking, no original prompt). Runs are kept whole; the window never opens mid-run; only ids below the trigger are read, scoped to the trigger's forum topic. Budgets are estimated tokens (UTF-8 bytes / 4).
- `runtime.py` runs one invocation: funder picks the tier (and thus the model role), the run row is opened, the window is built, the agent runs under hard caps (tool calls, per-request output tokens, wall time), the answer goes out via the sender, and `finish_run` closes the run with every provider response (failed runs included, via `capture_run_messages`). Failures get a short localized apology unless something was already delivered.
- `persona.py`: static persona text (cached prefix) + a dynamic situation block (place, topic, time, asker, chat profile framed as data).
- `deps.py`: `RunDeps` (chat, asker, reply target, funding, delivered outputs) and `Funding` → model role. `toolsets.py`: tool families register a `FunctionToolset[RunDeps]` with the tiers allowed to use them.
- `handler.py` is the last router: any invocation no command claimed goes to the runtime.
- Tests: e2e journeys swap the chat model through `Services.model_factory` (`tests/e2e/model.py` `ScriptedModel`); nothing in the offline suite calls a real model.
- `tools/`: one module per tool family, listed in `tools/__init__.py` `FAMILIES`. `tools/history.py`: `search_history`, `read_messages`, `chat_query`, `chat_info` (free, all tiers; current topic unless `whole_chat`). Tool output is capped and rendered with the same transcript lines as the window.
- `media.py`: images a run inspects — the current message's (album included) and the replied-to message's, or any stored message via the `inspect_media` tool. Vision pins (`RolePin.vision`) get the pixels; every inspected image without a note gets a one-line description (a separate small call on the run's own pin, ledgered as `kind='media'` against the run) stored on `message_media.description` and folded into `messages.extra_text`. Ambient media is never downloaded.
- `progress.py`: private chats stream the answer into a `sendRichMessageDraft` (throttled, `<tg-thinking>` step label, stop button); groups get one status reaction on the trigger (👀 thinking → 🤔 looking up → ✍ drawing → 👨‍💻 other tools; only standard reaction emoji are allowed) removed after the answer. Telegram refusals fall back to a typing indicator and never fail the run.
- Every run streams (an event handler is always passed), so a response cut off by stop or timeout is kept as `state='interrupted'`; `price_interrupted` asks OpenRouter for its cost by generation id and falls back to the pin's price snapshot. Stop (`stopped_message_generation`) cancels via the run's `CancellationToken`; the partial answer is posted and the run ends `cancelled`.
- `lanes.py`: runs queue per (chat, forum topic) so each sees the previous answer; while someone waits, their newer invoking message supersedes the older one (it is already in the newer run's window); a global semaphore (`settings.run_concurrency`) bounds runs in flight. `Runtime.answer` also skips triggers that already have a run (redelivered updates).
