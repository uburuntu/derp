# Agent

- `models.py`: `agent_runs` (one row per invocation: trigger, funding, served model, usage, cost, charge, Pydantic AI history) and `run_outputs` (every delivered message/poll/sticker/image/reaction, so `/info` resolves any output to its run). `runs.py` owns the run lifecycle: `finish_run` is the single place that ledgers a run's provider responses and stores its history; stored history replaces inline binary with markers, follows the chat's retention (`expire_run_messages`) and is dropped by privacy actions (`scrub_runs`); a run without history is replayed as its visible text. `ledger_side_call` ledgers model calls outside a run's own turns (media notes, digests, scout probes): every response, failed ones included, priced first.
- `invocation.py` decides what invokes Derp: every private message; in groups @mention/text mention, replies to Derp, or Derp's name (en/ru inflections and diminutives, not compounds). Bots never trigger (loop guard), anonymous admins do. Commands are a separate trigger kind handled by routers; `handler.py` is the last router: any invocation no command claimed goes to the runtime, a name-only one (`TriggerKind.NAME`, groups only) first through `Runtime.screen` — not addressed to Derp, nothing runs or is posted (no join notice, no unfunded offer, no chat action) and it never supersedes a waiting question.
- `decisions.py`: typed questions to the decision pin (Jev, `ModelRole.DECISION`) before a run, in one call with only those that apply: `addressed` (name-only triggers), `images` (fallback images only: `media.Referenced.fallback`), `effort` (rides along with any call; alone only on paid turns; deepens `chat_settings(effort=…)`, never lowers the pin's). State: the last `CONTEXT_LINES` transcript lines of the topic, the lines carrying fallback images and the new message, rendered as in the window. Thresholds, timeout and the switch are `settings.decisions` (tuned live on `tests/agent/name_mentions.json`; `pytest -m live` re-checks). Ledgered as creator-funded `kind='decision'` without a run; telemetry is `ops.observability.record_decision` (probabilities, outcome, duration). Any failure (timeout, error, unreadable answer) decides as if unasked: run, attach, the pin's effort.
- `lanes.py`: runs queue per (chat, forum topic) so each sees the previous answer; while someone waits, their newer invoking message supersedes the older one (it is already in the newer run's window); a global semaphore (`settings.run_concurrency`) bounds runs in flight. `Runtime.answer` also skips triggers that already have a run (redelivered updates).
- `context.py` builds the recent window before the current message: members' messages become `<chat_history>` transcript blocks (untrusted data), Derp's replies are replayed from their completed runs (tool calls + clipped results, no thinking, no original prompt; history that can't be loaded falls back to the visible text). Runs are kept whole; the window never opens mid-run; only ids below the trigger are read, scoped to the trigger's forum topic. Budgets are estimated tokens (UTF-8 bytes / 4). For prompt caching the runtime remembers each topic's window start per funding tier (`Runtime.window_starts`, in memory; tiers differ in budget and model) and keeps it while the window fits in `STICKY_SLACK` × the budget (rows too), so consecutive runs extend the same prefix; past that it starts afresh. Old lines must not change between runs: the transcript leaves out reaction totals (history tools show them), and replayed runs clip long tool results and long string arguments of tool calls (code, image prompts) deterministically.
- `runtime.py` runs one invocation (`Runtime._run`; a fresh one composes the window and request, an approved one resumes a paused run, see `approvals.py`): the money `Funder` reserves from the first payer that can cover a turn (no payer → `money.free.answer_unfunded`: the out-of-Derpcoins offer, in groups once per person per UTC day and a 🙈 reaction after that; no run), which fixes the tier and model role; the run row is opened, the window is built (first waiting, briefly, for voice transcriptions still running for earlier messages of its topic: `Transcriber.settle`), the agent runs under caps (tool calls, per-request output tokens, wall time, the money hold), the answer goes out via the sender (its `#id` references to stored messages linked in what Telegram shows, not in history: `history.links`), and `finish_run` closes the run with every provider response (failed runs included, via `capture_run_messages`). Failures — setup included — get a short localized apology unless something was already sent (a 429 on free models says they're busy; it and the money-cap notice say "not charged" only when nothing was charged, else that the work so far was), and any failure after the reservation releases the hold. A model that can't see images is told so in the situation block rather than guessing. Before each tool call the run's spend so far is checked against its hold; reaching it stops the run like a user stop (the backstop: `guard.py` wraps up first). `outputs.hold_left` is the one measure of what is left (side calls in the ledger, the run's turns, its fees and what kept results carry), read by the guard, that stop, web search and the paid tools. After delivery the run settles: charged if anything reached Telegram (parts of a half-sent answer included), released otherwise. A charge to a chat wallet that leaves it unable to pay a turn posts the silent empty-wallet line once (`money.free.note_empty_wallet`; approved actions too).
- `guard.py` (a per-run capability plus a model wrapper) makes caps end in an answer: at the soft caps (the tool calls allowed, requests, three quarters of the wall time, or a hold the next request would reach) requests go out with `tool_choice='none'` and a request-only note, schemas kept for the cache, and a tool called anyway is refused; a request the hold leaves no web search for (`tools.web.search_budget` is 0) gets an "out of budget" note; Pydantic AI's usage limits sit `BACKSTOP` above. Once per run, an unanswered reply (empty, thinking only, or cut off by the token limit before text or a complete tool call; the retry then gets double the output tokens) or a request the provider refused to start (429, 408, 5xx, connection) is retried on `RolePin.rotated()`, which serves the rest of the run, routed as that pin (a ceiling derived from the primary's price doesn't follow). A retry continues the run, so tools that ran are not repeated; errors after streaming began are not retried. `prefix.py` measures the prompt prefix (persona + the tier's up-front tool schemas + a fixed allowance) that turn prices add to the window: `Funder` minimums and `price_unreported`.
- `persona.py`: the persona is the only system instruction and never changes; the per-run `<situation>` block (place, topic, time, asker, rules, chat profile framed as data, and `memory.notes_block`: the chat notes policy on runs with memory tools, then the notes) opens the final request, after the window, so tools + persona + window stay a cacheable prefix. Members can't forge `<situation>` (`neutralize`). `deps.py`: `RunDeps` (chat, asker, reply target, `funds` with the funding tier and hold, `seen`: the messages whose images the run looks at, delivered outputs). `outputs.py`: the one path for outputs tools send (`deliver`: slot budget, send, record, ambiguity) and results kept for the next tool (`emit`, `flush`).
- `tools/` holds the tool families, their tiers and capabilities (see `tools/AGENTS.md`). `media.py`: images a run inspects — the current message's (album included) and the replied-to message's; when neither has one, the asker's immediately preceding stored message in the topic if sent within `FOLLOW_UP_SECONDS` (one message back, never deleted ones) and, for a reply to one of Derp's outputs, the images that run's trigger had by the same rules (one hop; shown but never described, since its line is older than the previous trigger and the window's old lines must stay byte-stable) — these fallback images are left out when a decision says answering doesn't need them; or any stored message via the `inspect_media` tool, which also sees videos, GIFs and video notes through one still frame (`derp.tools.effects.still`). A file that isn't a picture itself (an animated or video sticker, a GIF, a document) is seen through Telegram's preview picture (`message_media.thumb_file_id`), after the still frame when `inspect_media` takes one; every picture reaches the model normalized (`MediaGateway.image`). Those same images (`RunDeps.seen`) are what an edit or effect starts from when no message is named. Vision pins (`RolePin.vision`) get the pixels; every inspected image without a note gets a one-line description (a separate small call on the run's own pin, ledgered as `kind='media'` against the run, failed and empty responses included) stored on `message_media.description` and folded into `messages.extra_text`. A run's notes are made concurrently under a timeout; a paid note that came back empty stores `''`, so the image is never described (or paid for) again. Ambient media is never downloaded.
- `digests.py` builds day digests (see `history/digests.py`) on a cheap pin — sponsored, or free on free runs, resolved only when a digest is built — ledgered as `kind='digest'` against the asking run. Paid runs may build a week per tool call, others one day; a day too long for one call is summarized in parts and merged. The latest digest ending before the context window (if from the last few days) joins the situation block as data.
- `images.py` generates and edits images on the image pin via the Images API (paid funding only); the provider call is ledgered against the run only after Telegram accepted the photo, or for a result kept for a next step (`outputs.py`) the output made from it (otherwise absorbed as `creator`). `approvals.py`: actions above `approval_credits` or `approval_balance_fraction` of the payer's balance post a Make it / Cancel prompt (price only, never a balance) and pause the run on the call (Pydantic AI deferred tools: the tool raises `ApprovalRequired`, the run ends with `DeferredToolRequests` and stores its history); `approvals` rows keep the paused call's id and the priced job for `approval_minutes` and are deleted after a day. Only the requester decides, once. An expired prompt is turned into the expired notice without buttons, by the press that finds it or by `close_expired` (a bounded sweep every few minutes from `app.py`). An approval the payer can no longer cover turns its prompt into that note (`close_prompt`) with the buy button (`billing.menu.buy_button`: the personal menu in private, the chat's top-up in groups). Make it resumes the asking run as a new run (`Runtime.run_approved`, trigger `callback`): its stored history with `DeferredToolResults` approving that call (`resumption`; the job the prompt priced rides along as `tool_call_metadata`), so the image becomes the call's result and the model finishes the request (caption, sticker, cutout) under the usual slots, hold and charge-after-delivery. It is queued in the chat topic's lane so the run that posted the button has settled its hold, and funded afresh from the first payer whose paid Derpcoins cover the price plus a turn; the paused turn heads the new run's stored history (`finish_run(carried=…)`, not ledgered again) so replays pair call and result. Cancel and expiry cost nothing. Once the resumed run delivered something the prompt is deleted; otherwise its notices land on the prompt (failure note; a history dropped by privacy actions or retention can't be resumed and says it failed).
- `inline.py`: inline mode (one placeholder result with a keyboard so Telegram reports its `inline_message_id`; the answer is edited in on `chosen_inline_result`) and guest mode (one `answerGuestQuery` reply). Both use `Runtime.answer_detached`: the asker's personal funding, no chat history, only families marked `detached` (about, source, utilities: nothing that reads a chat or writes or sends anything; the brief names what is offered) plus the sandbox and web per tier, under the same `Guard`; no stored messages or run history; charged only after the answer is in.
- `progress.py`: private chats stream the answer into a `sendRichMessageDraft` (throttled, `<tg-thinking>` step label, stop button); groups get a chat action that follows the stage (`upload_photo` while drawing, `typing` otherwise) — never a status reaction, which would notify the asker. A refused draft falls back to the chat action; progress never fails the run. Every run streams (an event handler is always passed), so a response cut off by stop or timeout is kept as `state='interrupted'`; `runs.price_unreported` prices every paid response without a cost (cut off or not; runs, detached answers, digests, media notes): OpenRouter's cost by generation id, else its tokens at the pin's price snapshot; free-model responses stay 0. Stop (`stopped_message_generation`) cancels via the run's `CancellationToken`; the partial answer is posted and the run ends `cancelled`.
- Tests: e2e journeys swap the chat model through `Services.model_factory` (`tests/e2e/model.py` `ScriptedModel`); nothing in the offline suite calls a real model.
