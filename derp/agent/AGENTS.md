# Agent

- `models.py`: `agent_runs` (one row per invocation: trigger, funding, served model, usage, cost, charge, Pydantic AI history) and `run_outputs` (every delivered message/poll/sticker/image/reaction, so `/info` resolves any output to its run).
- `runs.py` owns the run lifecycle. `finish_run` is the single place that ledgers a run's provider responses and stores its history; stored history replaces inline binary with markers, follows the chat's retention (`expire_run_messages`) and is dropped by privacy actions (`scrub_runs`); a run without history is replayed as its visible text.
- Tools never receive `chat_id`/`user_id` arguments; scope comes from run dependencies.
- `invocation.py` decides what invokes Derp: every private message; in groups @mention/text mention, replies to Derp, or Derp's name (en/ru inflections and diminutives, not compounds). Bots never trigger (loop guard), anonymous admins do. Commands are a separate trigger kind handled by routers.
- `context.py` builds the recent window before the current message: members' messages become `<chat_history>` transcript blocks (untrusted data), Derp's replies are replayed from their completed runs (tool calls + clipped results, no thinking, no original prompt). Runs are kept whole; the window never opens mid-run; only ids below the trigger are read, scoped to the trigger's forum topic. Budgets are estimated tokens (UTF-8 bytes / 4). For prompt caching the runtime remembers each topic's window start (`Runtime.window_starts`, in memory) and keeps it while the window fits in `STICKY_SLACK` × the budget (rows too), so consecutive runs extend the same prefix; past that it starts afresh.
- `runtime.py` runs one invocation: the money `Funder` reserves from the first payer that can cover a turn (no payer → a plain notice, no run), which fixes the tier and model role; the run row is opened, the window is built, the agent runs under hard caps (tool calls, per-request output tokens, wall time), the answer goes out via the sender, and `finish_run` closes the run with every provider response (failed runs included, via `capture_run_messages`). Failures get a short localized apology unless something was already delivered (a 429 on free models says they're busy). A model that can't see images is told so in the situation block rather than guessing. Before each tool call the run's spend so far is checked against its hold; reaching it stops the run like a user stop. After delivery the run settles: charged if anything reached Telegram (parts of a half-sent answer included), released otherwise. Any failure after the reservation — setup included — releases the hold.
- `persona.py`: the persona is the only system instruction and never changes; the per-run `<situation>` block (place, topic, time, asker, rules, notes, chat profile framed as data) opens the final request, after the window, so tools + persona + window stay a cacheable prefix. Members can't forge `<situation>` (`neutralize`).
- `deps.py`: `RunDeps` (chat, asker, reply target, `funds` with the funding tier and hold, delivered outputs). `toolsets.py`: tool families register a `FunctionToolset[RunDeps]` with the tiers allowed to use them.
- `handler.py` is the last router: any invocation no command claimed goes to the runtime.
- Tests: e2e journeys swap the chat model through `Services.model_factory` (`tests/e2e/model.py` `ScriptedModel`); nothing in the offline suite calls a real model.
- `tools/`: one module per tool family, listed in `tools/__init__.py` `FAMILIES`; a `Family` names its tiers and which tools are deferred. Only free-model runs defer them (found via Pydantic AI's local `search_tools`, since OpenRouter has no native tool search); paid and sponsored runs load every tool, because revealing tools changes the tool list at the start of the prompt and breaks OpenRouter's prompt cache. `history.py`: `search_history`, `read_messages`, `chat_query`, `digest` (+ deferred `chat_info`, `inspect_media`); current topic unless `whole_chat`. `memory.py`: notes and admin chat rules (paid/sponsored). `web.py`: OpenRouter's `web_search` and `web_fetch` server tools as dynamic native tools (paid/sponsored only: search fees are in the response cost; fetch uses OpenRouter's own engine, never Derp's host). `inference.openrouter.DerpOpenRouterModel` maps `WebFetchTool`, which Pydantic AI doesn't for OpenRouter. `telegram.py`: output tools `send_poll` (quiz too), `send_dice`, `send_sticker` (chat favourites by emoji, then the global sticker index), `react`, all sequential and counted against `visible_outputs`; deferred ops edit/delete Derp's own messages and pin (admins). A final answer of just "." sends nothing when a tool output or reaction already answered.
- `media.py`: images a run inspects — the current message's (album included) and the replied-to message's, or any stored message via the `inspect_media` tool. Vision pins (`RolePin.vision`) get the pixels; every inspected image without a note gets a one-line description (a separate small call on the run's own pin, ledgered as `kind='media'` against the run) stored on `message_media.description` and folded into `messages.extra_text`. Ambient media is never downloaded.
- `digests.py` builds day digests (see `history/digests.py`) on a cheap pin — sponsored, or free on free runs — ledgered as `kind='digest'` against the asking run. Paid runs may build a week per tool call, others one day; a day too long for one call is summarized in parts and merged. The latest digest ending before the context window (if from the last few days) joins the situation block as data.
- `tools/code.py`: Pydantic AI Harness Code Mode as a pure sandbox — `run_code` runs Monty Python in a local worker with no Derp tools inside, no files, env, clock or network, capped time and memory; every tier, detached runs too. `tools/__init__.py` `CAPABILITIES` are run-wide: web, Code Mode, Harness `ToolOutputLimits` (clamps run_code and history tool results when produced) and `RepairToolArguments` (fixes malformed tool-call JSON). Prefer a core or Harness capability over hand-rolled plumbing; ours stay where money, Telegram delivery or OpenRouter specifics need them (image generation, spend holds, approvals, context window). `tools/utilities.py`: deferred toolbox over `derp/tools` (time zones, weather, rates, Wikipedia, Urban Dictionary, arXiv), plus WolframAlpha and the remote `run_program` only when their keys are set.
- `tools/games.py` (deferred): `post_polls` posts a series of up to 5 non-anonymous polls in one output slot — quizzes (scored, see `history/polls.py`) and/or regular polls; `most_likely_poll` offers the chat's most active members as options.
- `tools/effects.py`: deferred media effects over `derp/tools` (paid and sponsored runs): `make_meme` (picture, GIF, sticker or video; demotivator / lobster / panel), `reverse_media` (clips and voice backwards, pictures mirrored), `identify_anime`, plus `identify_song` (ACRCloud keys set), `remove_background` (weights present) and `profile_photo` (every tier). Sources (`tools/sources.py`) are a named stored message of this chat (Derp's own outputs included, so tools chain by the `#id` they answer with), else the trigger or the message it replies to, a member's profile photo (by message sender, never a user id) or the chat photo. Heavy effects (video encodes, cutouts) cost `effect_credits` on paid runs and are limited to `sponsored_effects_per_day` on sponsored ones; each becomes a `run_fees` row (0 credits on sponsored runs, which is what the daily count reads) only after Telegram accepted the result.
- `tools/about.py` + `guide.md`: `about_derp(topics)` (every tier, always loaded) answers questions about Derp itself — the hand-written concept guide (no digits, a test enforces it) plus facts generated at call time from settings, the command menus, the tool registry (`FAMILIES`, with tiers) and the en privacy/terms pages, so values can't go stale. Deferred `search_source` / `read_source` (paid, sponsored) read the shipped `derp/` package only (lookups by key, never by path) and link excerpts to `settings.source_url` at `source_revision` (set at image build).
- `tools/self_service.py` (deferred, every tier): `wallet_status` (the /credits card; by DM in groups, the model never sees amounts there), `purchase_button` (an exact Stars invoice, or the pack menu — a personal menu goes by DM from groups), `change_setting` (the /settings rules: admins for chat settings, context-off only posts the confirm button), `leave_feedback` (`ops.feedback`).
- `tools/scheduler.py`: `schedule` (+ deferred `list_jobs`, `cancel_job`, `resume_job`) over `derp/scheduler`.
- `images.py` + `tools/images.py`: `generate_image` (draw, or edit the current/replied/given message's image, a member's profile photo or the chat photo — Derp sends the result; bots can't set people's photos) on the image pin via the Images API; paid funding only. The provider call is ledgered against the run only after Telegram accepted the photo (otherwise absorbed as `creator`).
- `approvals.py`: actions above `approval_credits` or `approval_balance_fraction` of the payer's balance post a Run / Cancel prompt (price only, never a balance) instead of running; `approvals` rows keep the action's arguments for `approval_minutes` and are deleted after a day. Only the requester decides, once. Run funds the action afresh as its own run (`Runtime.run_approved`, trigger `callback`); Cancel and expiry cost nothing.
- `inline.py`: inline mode (one placeholder result with a keyboard so Telegram reports its `inline_message_id`; the answer is edited in on `chosen_inline_result`) and guest mode (one `answerGuestQuery` reply). Both use `Runtime.answer_detached`: the asker's personal funding, no chat history or function tools (web only), no stored messages or run history; charged only after the answer is in.
- `progress.py`: private chats stream the answer into a `sendRichMessageDraft` (throttled, `<tg-thinking>` step label, stop button); groups get a chat action that follows the stage (`upload_photo` while drawing, `typing` otherwise) — never a status reaction, which would notify the asker. A refused draft falls back to the chat action; progress never fails the run.
- Every run streams (an event handler is always passed), so a response cut off by stop or timeout is kept as `state='interrupted'`; `price_interrupted` asks OpenRouter for its cost by generation id and falls back to the pin's price snapshot. Stop (`stopped_message_generation`) cancels via the run's `CancellationToken`; the partial answer is posted and the run ends `cancelled`.
- `lanes.py`: runs queue per (chat, forum topic) so each sees the previous answer; while someone waits, their newer invoking message supersedes the older one (it is already in the newer run's window); a global semaphore (`settings.run_concurrency`) bounds runs in flight. `Runtime.answer` also skips triggers that already have a run (redelivered updates).
